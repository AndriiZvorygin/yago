## Abstract

Yago v0.0.66 reduces node disk writes during low-yield indexing. Unchanged recrawls no longer rewrite stored documents or disk-backed full-text entries. Identical vault records and read-only vault updates no longer commit storage pages. Anchor targets are re-indexed only when their inbound anchors change, cached peer results are written as one batch, and small Bleve flushes no longer rewrite mid-size segments. The optional web fallback now reports an honest empty answer instead of HTTP 409 when an engine answered without relevant rows. Builds use Go 1.26.10 with updated dependency and crawler package pins. No wire, setting or environment change is introduced. Existing full-text entries are re-indexed once on their next ingestion; no rebuild is required. Upgrade the node and crawler together.

## Changes

### Update the Go toolchain and dependency security baseline

Source, package and container builds now require Go 1.26.10, which carries the `crypto/x509` correction for CVE-2026-111943. Both product builder images pin the Go 1.26.10 Docker Official Image by digest, and the source-build requirement in the documentation is updated accordingly.

The node, crawler and crawl-contract module graphs pin `golang.org/x/net` v0.62.0, which addresses GO-2026-6860 and GO-2026-6866. The node and crawler graphs pin `github.com/klauspost/compress` v1.18.7, which addresses GO-2026-5841 (CVE-2026-63209). The minimum transitive updates are `golang.org/x/crypto` v0.58.0, `golang.org/x/sync` v0.24.0, `golang.org/x/sys` v0.49.0 and `golang.org/x/text` v0.43.0. The isolated end-to-end module graphs are tidied to the same baseline.

The crawler image replaces Alpine package pins that were withdrawn from the package index. It now pins `ca-certificates=20261020-r0` and `libexpat=2.9.0-r0`; the latter addresses CVE-2026-102633 and CVE-2026-77214. The complete pinned package set resolves on amd64 and arm64. Application behavior is not changed by these updates.

### Report an honest empty web answer instead of HTTP 409

These corrections apply only when an operator has enabled the optional web fallback. A Tavily-compatible `POST /search` returns HTTP 409 with `Retry-After: 1` when its sources retrieved no rows and at least one source was lost. Previously, the web engine race reported a lost source whenever any engine failed, even when another engine had answered without a verified row. The race now reports a lost source only when every engine that was not rate-limited failed. One answering engine makes the web stage an honest empty answer, so a request whose sources all answered without relevant rows returns HTTP 200 with an empty result list. A race in which every engine was rate-limited keeps its existing rate-limited outcome.

Web term coverage previously counted function words among its requirements. Natural-language questions could therefore reject relevant rows while admitting rows that matched only function words. When a query has at least two distinct content terms, only content terms now count toward and satisfy coverage, as identified by the node's existing multilingual stopword list. A query with fewer content terms keeps every word as a requirement.

The `auto` engine selection now starts DuckDuckGo HTML and hedges DuckDuckGo Lite, Brave and Mojeek. Bing is no longer part of `auto` because its organic rows almost never passed verification; `bing` remains an explicit engine choice. The Admin setting description, configuration guide, specification and ADR-0021 describe the new order.

### Skip unchanged document and full-text revisions

Before storing a canonical document, the document store compares every durable field with the stored row. These fields include the content hash, extraction generation, URLs, title, text, headings, links, inbound and outbound anchors, images, metadata, dates, clustering, and quality and safety evidence. When only the fetch and index timestamps differ, the row is not rewritten. The stored `FetchedAt` and `IndexedAt` values then remain those of the last substantive revision. Any other field difference updates the row as before. The canonical document is still passed to full-text indexing, so an interrupted earlier index write can be repaired.

The disk-backed full-text index records an identity of each entry's indexed form in its stored search candidate. Before a single or batch write, the index compares that stored candidate with the one it would write and skips the entry when they are identical. Missing, legacy, changed and previously failed entries are indexed. Repeated identities within one batch retain last-write ordering. After a failed write, skipping is disabled for that index shard until a later write on the same shard succeeds. This prevents a change that is visible but not confirmed as persisted from being treated as already stored.

The crawler interface is unchanged. Successful unchanged recrawls are still acknowledged and recorded for recrawl scheduling, and URL metadata and RWI delivery continue normally.

### Skip identical writes and read-only commits in the serving vault

A write to the serving sharded bbolt vault now compares the stored bytes with the new stored form and skips the record when they are identical. The comparison uses the raw stored value, so no additional value reads or decompression are introduced. Any difference, including a stored value that fails its integrity check, is still written. Collection lengths and the word filter are unaffected.

After the unchanged structural-root validation, an update now rolls back every physical shard transaction that materialized no storage changes and commits only changed shards. Read-only updates write no bbolt metadata pages and perform no fsync. Examples are stale-posting sweeps that find nothing to remove, recrawl profiles that already exist and due-work claims that find no work. A mixed update commits only its changed shards. Identical puts and deletes of absent keys no longer force a commit. Writer locks, read-modify-write atomicity, structural validation, rollback on failure and retries are unchanged. The explicit clean-shutdown checkpoint still commits every shard.

### Reduce full-text index writes from anchors, peer results and merges

Outbound anchor replacement now records the targets that the previous publication of a source linked. A stored target is offered to the index only if one of three conditions holds: its stored inbound anchors change, the replaced source previously linked it, or its retained anchors include a replaced source. A target linked by more sources than the inbound-anchor cap is therefore no longer rewritten for every new linking source. A replay after a failed visit still re-indexes targets whose store mutation was committed earlier. Search results and anchor text are unchanged.

When remote results are cached after a swarm search, the node first collects the new results. It skips blank, repeated and already stored URLs. It then checks growth admission once, stores the results in one write and indexes them in one batch when the index supports batching. Other indexes still receive one document at a time. A swarm search therefore produces at most one new index segment per touched shard for its cached peer results. Existing rules are unchanged: a stored URL is never overwritten, at most two cache operations run concurrently and each has a 30-second deadline.

The disk index merge plan now sets an explicit 2 MiB segment floor. Previously the floor followed the 32 MiB persister memory cap, so a flush of one or two documents could re-merge mid-size segments. Existing shards now open with the current Scorch configuration, so the policy also applies to indexes created by earlier releases. The persister memory cap, the 100,000-document merged-segment ceiling and startup consolidation are unchanged. Flushes beyond the tier budget still merge.

### Share one JSON codec across vault record collections

Plain vault record collections now share one JSON codec. The three validating codecs for API keys, lease control targets and saved crawl profiles reuse its encoder and keep their own validating decoders. Stored bytes and decode behavior are unchanged, and corrupt values still surface as corrupt-value errors. A record that JSON cannot encode is now reported as a vault write error. Several previous codecs ignored that error and could have persisted an empty value.

### Add regression and mutation coverage

New tests cover known-result snapshot cancellation deterministically. They also pin three behaviors: the disk index's post-filter scan decision, blank-query and non-positive page-size handling, and the retention of legacy inlinks for targets without an inbound anchor record. Unreachable complete-scan, facet and conditional-total branches were removed from the paged hit collector, which is reached only without facets or post-filters. Search results are unchanged.

## Compatibility

- No YaCy, Tavily or node-crawler message shape changes. A Tavily-compatible search whose web sources answered without relevant rows now returns HTTP 200 with an empty result list instead of HTTP 409. A search that retrieves no rows while a source is lost keeps the existing HTTP 409 response with `Retry-After: 1`.
- No setting, environment variable, listener, service, image repository, database bucket or new dependency is added. The meaning of `auto` for the web-fallback backend setting changes as described above; existing values remain valid.
- The stored full-text search candidate gains an optional indexed-form identity field. Entries written by earlier releases lack it and therefore compare as changed, so each is re-indexed once on its next ingestion. No index rebuild is required. The document store row format is unchanged.
- Stored `FetchedAt` and `IndexedAt` describe the last substantive revision, not the latest unchanged recrawl. The values shown in Admin document views and index exports follow this rule, and so does the date on the cached-page view. Recrawl scheduling continues to record every successful fetch.
- Source builds require Go 1.26.10.
- The reusable-module API gate compares against the exact previous published v0.0.65 tag and source commit.

## Upgrade and rollback

Verify the published package's GitHub-hosted attestation against repository `D4rk4/yago`, the exact release workflow, tag ref and source commit. Use matching node and crawler binaries. Preserve configuration and data; ordinary deployments should use the established stopped-service backup procedure. Where an explicit target-specific operator policy omits a new pre-upgrade backup, preserve every existing archive unchanged.

Stop the crawler and node, install the published package, then start and verify the node before starting the crawler. The package enables the units but does not start them automatically. After the upgrade, the first ingestion of each existing document rewrites its disk-backed full-text entry once to record the new identity field. Unchanged documents are then skipped on later recrawls.

Rollback reinstalls the previous verified matching package with both services stopped. The older version ignores the unknown candidate field and reads the unchanged document and vault formats. It rewrites unchanged documents and full-text entries as before and opens existing index shards with their stored configuration rather than the current merge policy. Entries it rewrites lose the identity field and are re-indexed once again after a later upgrade. `FetchedAt` and `IndexedAt` values retained by this release are not restored to the time of the latest recrawl.

## Known limitations

- The in-memory full-text backend still rewrites unchanged entries, and only the disk index skips identical writes. The dedicated crawl-broker database, the crawler frontier and the in-memory vaults do not skip identical writes or read-only commits.
- A successful vault update that changes nothing still invalidates the vault's cached storage-capacity measurement.
- After a failed index write, the affected shard rewrites every entry it receives until a write on that shard succeeds.
- Disk index shards may hold more small segments between merges than before.
- Open bug issue #3, concerning memory usage, remains deferred: its unchanged historical evidence does not establish a current reproducible defect requiring a separate memory-policy change in this candidate.
