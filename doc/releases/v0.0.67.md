## Abstract

Yago v0.0.67 restores swarm results in the default web-fallback supplement mode. The exact local-plus-peer stage now has up to 1400 milliseconds in every fallback mode; supplement mode starts web retrieval beside a stage that has not finished by its 600-millisecond decision point instead of canceling peer calls. The peer roster moves to its own storage file so its writes no longer wait behind indexing; existing roster rows are copied once on first start. Anchor-text maintenance keeps submitted inlinks from other sources and replaces stale text on targets without an anchor record. Internal refactors carry no behavior change. No wire, setting, environment, listener or dependency change is introduced. Upgrade the node and crawler together.

## Changes

### Let slow peers finish before the web supplement decides

In supplement mode ("Supplement below 100 results") the whole exact local-plus-peer stage was previously capped at 600 milliseconds. Peers are asked for answers within 1200 milliseconds and in observed operation replied in roughly 550 to 990 milliseconds, so peer calls were canceled and only web rows reached the user; slow local searches were cut in the same way.

The exact stage now has up to 1400 milliseconds in every web-fallback mode. Supplement mode waits for that stage until a decision point of 600 milliseconds, shortened when needed so that one second of web retrieval and 100 milliseconds of assembly remain inside the 1.8-second request deadline. A stage that completes before the decision point keeps the existing rule: web retrieval runs only when fewer than 100 verified unique candidates exist. A stage still running at the decision point continues while web retrieval starts beside it, and both answers are merged through the same completion path used by the `always` mode. The `always` mode is unchanged.

### Keep the peer roster in its own storage file

The peer roster shared the main sharded vault with crawler ingest. Under ingest load its short-deadline writes timed out waiting for write admission, so callers were not recorded, reachability was not confirmed and unreachable peers were not removed. The roster now lives in `peerroster.db` under the data directory. On the first start with this release the three roster buckets are copied from the main vault in pages, the copy is verified against the source, and a completion marker is written; later starts copy nothing. The main vault is only read during the copy, so a failed copy stops startup without altering existing rows, and an interrupted copy resumes on the next start. Peer news, transfer tallies and the peer blocklist remain in the main vault.

### Correct anchor-text maintenance

An outbound-anchor replacement now keeps anchor text submitted for a stored target by other sources and supersedes only the anchors of the replaced source. An outbound-anchor update now also replaces the replaced source's stale anchor text on a target that has no anchor record yet; previously the stored text could remain stale.

### Internal refactors without behavior change

Remote crawl queue index scans share one generic pass; crawler fleet settings are sent through one broadcast routine; canonical batch reads and terminal delivery revisions share one workflow; crawler duration settings are declared as data and the two search-model rollbacks share one endpoint; size-bounded reads and key deletion are shared across peer mail and news. Some internal error texts now name the storage bucket; error identities that callers check are unchanged.

## Compatibility

- No YaCy, Tavily or node-crawler message shape changes.
- No setting, environment variable, listener, service, image repository or new dependency is added.
- A new data file, `peerroster.db`, is created under `YAGO_DATA_DIR`. The roster buckets in the main vault are retained but no longer used after migration.
- In supplement mode, web retrieval may now start when the exact stage has not completed by the decision point, even if that stage later yields 100 or more candidates. Supplement mode therefore issues somewhat more web requests on slow queries than v0.0.66, while it no longer drops peer and slow local rows.
- The reusable-module API gate compares against the exact previous published v0.0.66 tag and source commit.

## Upgrade and rollback

Verify the published package's GitHub-hosted attestation against repository `D4rk4/yago`, the exact release workflow, tag ref and source commit. Use matching node and crawler binaries. Preserve configuration and data; ordinary deployments should use the established stopped-service backup procedure. Where an explicit target-specific operator policy omits a new pre-upgrade backup, preserve every existing archive unchanged.

Stop the crawler and node, install the published package, then start and verify the node before starting the crawler. The package enables the units but does not start them automatically. The first node start copies the peer roster into `peerroster.db`; the copy is proportional to the roster size.

Rollback reinstalls the previous verified matching package with both services stopped. The older version ignores `peerroster.db` and uses the roster rows left in the main vault, which reflect the state at the time of the upgrade. Roster changes made under this release are not visible to the older version. A later re-upgrade finds the completion marker, uses `peerroster.db` again and does not copy roster rows written by the older version.

## Known limitations

- Supplement mode cannot count candidates from a stage that is still running at the decision point, so it may start web retrieval for a query whose stage later reaches 100 candidates.
- Peer news, transfer tallies and the peer blocklist still share the main vault and may meet the same write-admission delay under heavy ingest; this has not been observed in production warnings.
- Bug #3 (node memory use) remains open; this release does not change memory behavior.
